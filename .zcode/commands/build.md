description: Implement tasks incrementally from module chunks — build, test, verify, commit. "auto" runs every task of one module in one unattended run.
---

Load the `incremental-implementation` skill alongside `test-driven-development` with the `skill` tool, then discover the task's tech stack and load every additional skill the `Intent → skill mapping` in AGENTS.md calls for (see below).

## Artifact layout (see AGENTS.md "Spec & task artifacts")

- `SPEC.md` — master index: capability map, dependency direction, build order, per-module status.
- `SPEC-<module-id>.md` — a module's approved spec.
- `tasks/<module-id>.md` — the module's task chunk: the unit `/build` consumes.
- `tasks/plan.md` / `tasks/todo.md` — global aggregates generated by `/planning`.

## Step 0 — select the mode from the invocation

Arguments received: `$ARGUMENTS`

Decide the mode **before doing anything else** — it determines which procedure below you run. Never start the single-task loop and "upgrade" to autonomous mid-run.

| Invocation | Mode |
|---|---|
| *(empty)* | single task of the next pending module (build order from `SPEC.md`) |
| `<module-id>` | single task of that module |
| `auto` | autonomous run of every task of the **next pending module** |
| `auto <module-id>` | autonomous run of every task of that module |

There is no whole-initiative mode; running modules one at a time is the workflow. Autonomous mode is not faster *per task* — same test-driven loop — it only removes human stepping *between* tasks.

Chunks are the **only** source of tasks. If `SPEC.md` or the target module's `SPEC-<module-id>.md` / `tasks/<module-id>.md` don't exist, stop and point at `/spec` / `/planning` — never invent tasks from `ROADMAP.md`, the codebase, or anywhere else.

## Tech-stack discovery → skill mapping

Before writing any code, work out what the task actually involves, then let the `Intent → skill mapping` in AGENTS.md decide which skills to load on top of `incremental-implementation` + `test-driven-development`.

1. **Detect the stack.** Read `Cargo.toml` and the files the chunk lists to pin down what the task touches — plain Rust logic, libcosmic / COSMIC APIs, Wayland layer-shell, config parsing, or the PTY/terminal engine.
2. **Map the intent.** Consult the `Intent → skill mapping` in AGENTS.md and load every skill the task's intent matches. For this repo that means:
   - Rust code / review → `rust-best-practices` (load for every Rust task)
   - New module boundary or public interface → `api-and-interface-design`
   - Untrusted input, auth, secrets, config → `security-and-hardening`
   - Performance-sensitive path or suspected regression → `performance-optimization`
3. **Verify unfamiliar APIs.** When the task calls a libcosmic / COSMIC API you'd otherwise write from memory, ground it in official docs (`source-driven-development`) rather than trusting training data.

The mapping — not this file — is the authority on which skill governs an intent. If the task matches an entry listed there, load it.

## Single task (default, `/build`, `/build <module-id>`)

1. Pick the next pending task: read `SPEC.md` status, then the module's `tasks/<id>.md` chunk.
2. Load the chunk's context: its `SPEC-<id>.md`, the files it lists, existing patterns.
3. Discover the task's tech stack and consult the `Intent → skill mapping` in AGENTS.md, loading every skill the task's intent matches (see "Tech-stack discovery → skill mapping").
4. Write a failing test for the expected behavior (RED).
5. Implement the minimum code to pass the test (GREEN).
6. Run the full test suite to check for regressions.
7. Run the build to verify compilation.
8. Commit with a descriptive message.
9. Mark the task complete in the chunk, in `tasks/todo.md`, and in `SPEC.md`'s status table; stop.

## Autonomous: one whole module (`/build auto`, `/build auto <module-id>`)

Use this once a module's spec is approved and its chunk written, to collapse plan + build for that module into one run. Every task still earns a passing test and its own commit.

1. **Require an approved spec and a chunk.** The module must be marked approved in `SPEC.md` and have `SPEC-<module-id>.md` + `tasks/<module-id>.md`. Otherwise stop and point at `/spec` / `/planning` — do not invent requirements.
2. **Enforce build order.** If the module has pending dependencies, stop and name them.
3. **Establish a clean baseline.** Run `git status --porcelain`. If there are uncommitted changes outside the expected working artifacts (`SPEC*.md`, `tasks/`), stop and ask the user to commit, stash, or confirm. Autonomous per-task commits must not absorb unrelated local work.
4. **Announce the run, then start immediately.** State the module and list its chunk's tasks once so the run is visible in the transcript, then begin the task loop without waiting for approval. The stop-conditions in step 6 are the only thing that may interrupt the run.
5. **Task loop — repeat until the chunk has no pending tasks left.** Pick the next unchecked task in the chunk and run the full single-task procedure on it (discover stack → map skills → RED → GREEN → regression suite → build → commit → mark complete in the chunk, `tasks/todo.md`, and `SPEC.md`'s status table). After each commit, re-read the chunk to find the next unchecked task and **immediately continue** — do not stop between tasks, do not ask for approval, do not summarize early. Stage only the files that task touched plus its status updates — never `git add -A` blindly — one commit per task so any point is a clean rollback. The loop ends only when the chunk is exhausted or a stop-condition in step 6 fires.
6. **Stop and ask the user** (do not push through) when:
   - a test can't be made to pass or the build breaks without an obvious fix → follow `debugging-and-error-recovery`
   - the spec is ambiguous, or a task needs a decision the spec doesn't cover
   - a task is high-risk or irreversible — anything touching secrets, destructive operations, or that you can't undo with `git revert` → follow `doubt-driven-development` and get explicit sign-off

   After the user resolves a blocker, they re-invoke `/build auto` — it resumes from the next pending task.
7. **Summarize at the end:** tasks completed, tests added, commits made, anything skipped, flagged, or left for the user.

If any step fails, follow the `debugging-and-error-recovery` skill.
