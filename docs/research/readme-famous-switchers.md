# Famous window-switcher READMEs

**Question:** How do famous, high-star window-switcher/Alt+Tab/window-management tools structure their READMEs, and what transfers to Airlock's?
**Date:** 2026-11-14
**Status:** Complete — 8 primary-source READMEs from the famous tier (437 to 40.7k stars), compared against the 11-peer small-peer survey in [readme-peer-tone.md](readme-peer-tone.md); transfer verdicts for Airlock's Features section in §3.

**Method:** primary sources only — each tool's own README fetched from its repository default branch via raw.githubusercontent.com (full text read, not summarized), plus the GitHub API (`api.github.com/repos/<org>/<repo>`) for star counts and default branches, plus the repo HTML pages where the README's rendered existence itself was in question. All fetches 2026-11-14; stars are pinned to that date. Difference from the peer-tone record's yardstick: that survey ran `wc -w` on the raw bytes; this session had no shell, so word counts below are my estimates from the full fetched text and are marked with `~` — structure facts (heading trees, badge lists, placement) are exact from the fetched bytes. Repo existence was verified via the API (full_name, default_branch) rather than search.

---

## Findings

### Per-tool structure inventory

Ordered by task list, which puts the closest category match first. Stars from the GitHub API, 2026-11-14.

#### 1. lwouis/alt-tab-macos — 16,530 stars, default branch `master`

The closest category match (Windows-style Alt+Tab on macOS) has effectively **no README**. The entire file is two images: a hero SVG banner (alt text: "AltTab Pro — 7.4M downloads — 15K GitHub stars — Get AltTab") linking to [alt-tab.app](https://alt-tab.app), and a "Sponsored by JetBrains" badge. ~35 words, zero Markdown headings, zero prose. Verified twice (full-text fetch + repo page render: no README text visible, About sidebar links alt-tab.app).

The real front door is the website: hero tagline "Find the right window. Keep your flow.", sections "Keep your mind on what matters", "8 years of refinement", "Questions" (FAQ). Features are 4 items, each a short bold-style lead plus one-to-two sentences — "Every window, not just every app", "Preview before you switch", "Styles" (Pro tag), "Search" (Pro tag). Two carry paid-tier tags; one item reads "Minimized, hidden, on another Space. They're all in the switcher"; the page also states "No tracking, no telemetry". This is a storefront, not a README.

#### 2. rxhanson/Rectangle — 30,280 stars, default branch `main` (fetched via the `master` path, which served current content — see Unverified)

~1,500 words (estimate), ~21 headings. Heading tree, in order: `# Rectangle` → 1 CI badge → one-sentence description → **screenshot** → `## System Requirements` → `## Installation` (dmg link + `brew install --cask rectangle` code block) → `## How to use it` (prose + a snap-areas **table** + `### Ignore an app` as numbered steps) → `## Execute an action by URL` (prose + ~60 enumerated action names) → `## Terminal Commands for Hidden Preferences` (one link out) → `## Differences with Spectacle` (6 bullets) → `## Common Known Issues` (3 `###` issues + `### Troubleshooting` as numbered quick-fixes) → `## View Debug Logging` → `## Import & export JSON config` → `## Preferences Storage` → `## Uninstallation` (`defaults delete` + `brew uninstall --zap` code blocks) → `## Contributing` (3 `###` subsections) → `## Credits`.

Install sits before usage. There is **no feature list at all** — "features" are taught as usage: prose, a table ("Left or right edge → Left or right half"), and numbered steps. Quotes: "Rectangle is a window management app based on Spectacle, written in Swift." / "The keyboard shortcuts are self explanatory, but the snap areas can use some explanation if you've never used them on Windows or other window management apps." Notably it ships **both an Uninstallation and a Troubleshooting section** — absent from all 11 small peers (peer-tone record §3).

#### 3. pop-os/shell — 5,290 stars, default branch `master_noble` (version-branched repo; fetched from `master`, content current — see Unverified)

~1,900 words (estimate), ~26 headings — the longest *prose* README in the set and the ecosystem neighbor (Pop!_OS's own shell). Tree: `# Pop Shell` → **3 intro paragraphs of manifesto** → screenshot → `## Table of Contents` (annotated bullet TOC — the only TOC in the famous set) → `## The Proposal` → `## The Problem` (4 `###` subsections: "Displays are large, and windows are many", "Displays are large. Very, **very** large", "Fighting the window manager is futile", "Why not switch to i3wm?") → `## Installation` (branch-selection bullets, `make local-install`, an in-section uninstall paragraph: "If you want to uninstall the extension, you may invoke `make uninstall`…") → `### Packaging status` (per-distro bullets: Fedora/Gentoo/openSUSE/Arch with commands) → `## Shared Features` (7 `###` subsections, each a behavior: Directional Keys, Overridden GNOME Shortcuts as 8 `` `Super` + key `` bullets, Window Management Mode, Window Focus Switching, Launcher, Inner and Outer Gaps, Hiding Window Title Bars) → `## Floating Mode` (2 `###`) → `## Tiling Mode` (prose + Keyboard Shortcuts + config-file example) → `## Developers` → `## License`.

Features are presented as **keybind-behavior documentation**, not a list: every capability is a `Super`+key bullet or a named mode explained in prose. Quotes: "The core feature of Pop Shell is the addition of advanced tiling window management — a feature that has been highly sought within our community." / "Tiling window management in GNOME is virtually nonexistent, which makes the desktop awkward to interact with when your needs exceed that of two windows at a given time."

#### 4. hyprwm/Hyprland — 40,654 stars, default branch `main` (biggest in the set)

~350 words of prose (estimate; the file is image/link-heavy). Tree: SVG banner → **6 badges** (CI workflow, license, language, PRs, issues, "Hi mom") → two-sentence description → horizontal rule → **big nav link row** (`Install`, `Quick Start`, `Configure`, `Contribute` — all four pointing at the wiki, not the README) → `# Features` (one flat bullet list, ~25 bullets, no bold leads, ends "and much more...") → `# Gallery` (3 screenshots) → `# Special Thanks` (6 bold credit entries, e.g. "**[dwl]** - *For showing how 2 do stuff the hacky way*") → ~25 lines of link-reference definitions.

**No install section in the README at all** — delegated to the wiki via the nav row. The feature list is the only famous-README feature catalog: short noun phrases, one per bullet — "Tearing support for better gaming performance", "Socket-based IPC", "Special workspaces (scratchpads)", one nested sub-list for layouts (Dwindle/Scrolling/Master/Monocle/custom). No bold leads, no per-feature screenshots; visuals live in a separate Gallery. Quote: "Hyprland is a 100% independent, dynamic tiling Wayland compositor that doesn't sacrifice on its looks."

#### 5. asmvik/yabai (formerly koekeishiya/yabai — the API's `full_name` is `asmvik/yabai`; the old org redirects) — 29,838 stars, default branch `master`

~750 words (estimate), 5 h2s. Tree: SVG banner → **5 badges** (license, documentation, wiki, changelog, version) → one-liner ("Tiling window management for the Mac.") → `## About` (**screenshot** at the top of the section + 2 paragraphs) → `## Installation and Configuration` (**3 bullets, all links out** to the wiki, docs, examples — zero commands in the README) → `## Requirements and Caveats` (two dense tables: supported macOS versions per arch, and caveats incl. System Integrity Protection) → `## License and Attribution` → `## Disclaimer` ("Use at your own discretion.").

No feature list; capabilities are folded into About prose: "The primary function of yabai is tiling window management; automatically modifying your window layout using a binary space partitioning algorithm to allow you to focus on the content of your windows without distractions." The Requirements/Caveats tables are the set's most operational content — everything risky about the tool is documented up front in table form.

#### 6. LGUG2Z/komorebi — 15,377 stars, default branch `master`

~3,000+ words including code samples (estimate) — the largest README in the set. Tree: `# komorebi` → tagline ("Tiling Window Management for Windows.") → **10 badges** (Tech for Palestine, workflow, downloads, commits-since-release, active commercial licenses, Discord, sponsors, Ko-fi, Notado, YouTube) → screenshot → 3 `## Note:` sections (MDM students, MDM prompts, komorebi for Mac) → `## Overview` (3 paragraphs + a links paragraph into the docs site: installation, configuration, workflows, config schema, CLI reference) → `## Community` (Discord/YouTube/Awesome List) → `## Licensing for Personal Use` → `## Sponsorship for Personal Use` → `## Licensing for Commercial Use` → `# Installation` (**one paragraph linking to the docs site** + a walkthrough-video embed) → `# Comparison With Fancy Zones` (video embed) → `# Demonstrations` (3 community videos with credits) → `# Contribution Guidelines` (commit hygiene, PR rules, refactor approval, breaking-change ban — "No user should ever find that their configuration file has stopped working after upgrading to a new version of `komorebi`.") → `# Development` → `# Logs and Debugging` (incl. `## Restoring Windows`, `## Panics and Deadlocks`) → `# Window Manager State and Integrations` → `# Window Manager Event Subscriptions` (Named Pipes / Unix Domain Sockets / Rust Client / schemas / TCP — long code samples) → `# Appreciations`.

Install is a link plus a video. **No feature list**; the Overview prose carries the positioning ("aims to make _as few modifications as possible_ to the operating system… these will remain opt-in and off-by-default"). Length comes from contributor policy and integration API docs, not marketing.

#### 7. stefansundin/altdrag — 1,639 stars, default branch `master`, last push 2024-11-12 (dormant, not archived)

**No README exists.** The root file listing (GitHub contents API) contains no README file, and the repo page renders only the GPL license — no README headings or content. The About sidebar points to [stefansundin.github.io/altdrag/](https://stefansundin.github.io/altdrag/), which is the front door: sections Note (Windows-only disclaimer) / Donate / News / What is AltDrag? / New languages / Support / License / Credits. Tagline: "Easily drag windows when pressing the alt key". Intro: "After starting AltDrag, you can simply hold down the Alt key and then click and drag any window." It will resize from the corner or edge you grab closest to."), with deeper material deferred to separate doc pages.

#### 8. sagb/alttab — 437 stars, default branch `master` (the `alttab` X11 switcher; same project as the peer-tone record's §2.11)

Structure unchanged since the peer-tone record's 2026-11-06 mechanical read (236 words by `wc -w` — reused here as the only exact count in this survey). Re-fetched 2026-11-14: **three screenshots before any text** at the very top, CI badge, one-sentence description ("**alttab** is X11 window switcher designed for minimalistic window managers or standalone X11 session."), the full usage synopsis as a code block followed by "(see man page for details)", the why-paragraph ("Unlike task switchers integrated in most simple window managers (WM) or dmenu-like switchers, alttab features visual interface and convenient tactile behaviour: press modifier (Alt) - multiple switch with a key (Tab) - release modifier."), then `# Installation` (clone/configure/make + links to INSTALL.md, wm-setup, mobile docs) and `# See also`. Two headings total; the man page carries the depth. Only visible deltas from the record's fetch: the copyright line now reads "2016-2026" and `# See also` gained a no-wm link.

### Cross-tool patterns

**The famous tier treats the README as a landing page; depth lives elsewhere.** Five of eight delegate their real documentation: alt-tab-macos → website (README is a banner), altdrag → GitHub Pages site (no README at all), Hyprland → wiki (nav link row, no install section), yabai → wiki (link bullets, no commands), komorebi → docs site (one link + video). Only Rectangle and pop-os/shell keep actual instructions in the README. This inverts the small-peer norm from the peer-tone record, where 10 of 11 keep an install/build section with code blocks in the README — delegation is what fame buys you (a wiki, a docs site, a storefront), not a README virtue to emulate at every scale.

**Every README that exists opens with a one-sentence description — same as the peer norm.** Rectangle ("…window management app based on Spectacle, written in Swift."), yabai ("Tiling window management for the Mac."), komorebi ("Tiling Window Management for Windows."), Hyprland ("…dynamic tiling Wayland compositor that doesn't sacrifice on its looks."), alttab ("**alttab** is X11 window switcher designed for minimalistic window managers or standalone X11 session."). The peer record's "X is a Y for Z" shape holds at 40k stars.

**Screenshot placement: immediately after the description, before any section** — Rectangle, komorebi, yabai (top of About), pop-os/shell (after 3 intro paragraphs), alttab (three screenshots before any text). Hyprland is the outlier with a Gallery *after* Features; alt-tab-macos has no screenshot at all, only a marketing banner. The peer record found the same split (6/11 near-top) — the near-top convention is tier-independent.

**Badge rows scale with fame, not information: 0, 1, 1, 5, 6, 10.** pop-os/shell has none; Rectangle one CI badge; alttab one CI badge; alt-tab-macos one sponsor badge; yabai five; Hyprland six (incl. a joke "Hi mom"); komorebi ten (incl. downloads and a live commercial-license counter). The peer record found badges in only 4/11 small peers. More fame, more badges — and none of them carry install-or-usage information except fuzzel's repology badge from the peer set.

**Install sits before features/usage in every README that keeps real instructions.** Rectangle: System Requirements → Installation → How to use it. pop-os/shell: Installation → Shared Features. alttab: description + usage synopsis → Installation (usage synopsis doubles as the feature surface for a switcher, so the order still reads install-early). The link-out READMEs don't order it at all. No famous README buries install after a feature catalog.

**Features presentation has no single famous pattern — but none of them is Airlock's.** The variants observed: flat noun-phrase bullets, no bold leads (Hyprland, the only true list); keybind-behavior subsections (pop-os/shell); usage-first prose + table + steps, no list (Rectangle); capabilities folded into About prose (yabai); nothing (komorebi, alt-tab-macos README, altdrag README). The bold-lead one-liner format — "**Lead** — one sentence" — appears in this survey only on alt-tab.app's *website* features (4 items) and in fuzzel's README from the peer set (40+ bullets across three subsections), not in any famous README itself.

**Word counts: famous median ~750 (estimates), vs. peer median 183 — but the informative core stays small on both tiers.** Sorted estimates: ~35 (alt-tab-macos), 236 (alttab, exact), ~350 (Hyprland), ~750 (yabai), ~1,500 (Rectangle), ~1,900 (pop-os/shell), ~3,000+ (komorebi). What makes the long ones long is operational content — yabai's caveats tables, komorebi's contribution policy and event-subscription API docs, Rectangle's ~60 URL action names and troubleshooting walks — not narrative prose. The peer record's fuzzel observation ("earns its 622 words with a feature catalog in bullets and a build walkthrough in code blocks") is the same mechanism.

**Uninstall/Troubleshooting: the "0 of 11" peer norm is a small-project artifact, not an iron law.** At the famous tier: Rectangle ships both (`## Uninstallation`, `### Troubleshooting` with numbered quick-fixes); pop-os/shell documents uninstall inside Installation (`make uninstall` + "Reset All…" instructions); komorebi ships Logs/Debugging with a window-restore recovery path. All three are tools that, like Airlock, take over system behavior (shortcuts, window management) — which is presumably why they document the undo.

### Transfer to Airlock

**Worth copying / keeping:**

1. **Keep the one-sentence description opener; consider moving the payoff clause into Why.** Every famous README and all 11 peers open with a single plain sentence. Airlock's current opener is one sentence plus a purpose clause ("…the switcher lists and cycles only the windows on the **current workspace**, so nothing you parked elsewhere leaks into your focus."). The famous tier caps the opener at the "what it is" — Rectangle even splits Spectacle-derivation into its own clause-free sentence. Airlock's second half is good material, but it duplicates the Why section's first bullet.
2. **Keep the screenshot directly under the description** — five of eight famous tools place it exactly there (Rectangle, komorebi, yabai, pop-os/shell, alttab), matching the peer record's 6/11. Airlock already does this. No change.
3. **Keep install code blocks in the README, before Features.** The famous delegation pattern (Hyprland/yabai/komorebi) is a function of owning a wiki/docs-site/storefront; Airlock's docs are a handful of Markdown files, and both tiers agree simple installs belong in the README (10/11 peers; Rectangle, pop-os/shell). But note the ordering disagreement: every famous README that keeps instructions puts Install before usage/features, while Airlock runs Features → Install and the peer set's one feature-catalog README (fuzzel) also runs Features → Installation. Both orders have tier-appropriate precedent; the famous tier's install-early reads as "this is an app you install", the fuzzel order as "this is a catalog you browse". Flagging the disagreement, not resolving it.
4. **Keep Uninstall and Troubleshooting, but compress them toward Rectangle's weight.** The peer record's "0 of 11" made these sections look like Airlock idiosyncrasies; the famous tier shows they are standard for tools that rebind system shortcuts (Rectangle's Uninstallation is ~50 words plus two code blocks; its Troubleshooting is numbered quick-fixes; pop-os/shell covers uninstall in two sentences inside Installation). Airlock's byte-for-byte guarantee narrative ("a `custom` file install created is deleted again, and an asset file you edited by hand is kept and named") is worth one bullet, not a paragraph — the peer record's own lever (move prose to `docs/`, link one line) applies here, and Rectangle's one-line "See [TerminalCommands.md]" is the famous-tier version of exactly that move.
5. **The bold-lead feature bullet is a validated format for this product category — keep Airlock's Features list, and consider tightening toward Hyprland's noun-phrase brevity.** Hyprland proves the flat bullet catalog works in a 40k-star README ("Socket-based IPC", "Tearing support for better gaming performance"); alt-tab.app proves the bold-lead one-liner ("**Preview before you switch**"-style leads with 1–2 sentences) is how the category leader presents features once it owns a landing page. Airlock's current bullets sit between the two: bold lead + 1–2 lines, with inline config-key references (`layout = "horizontal"`, `rows`, `font_size`). The config-key linkage has no famous-README precedent (famous tools push all config to docs/wiki — komorebi links a "complete configuration schema reference" instead of inlining keys), but it matches Airlock's peer-tier constraint of having no separate config site; it also duplicates what docs/settings.md already carries. If Features feels heavy, the famous-tier move is: shortnoun-phrase bullets, keys linked once at the section's end (Airlock already has the "how the switcher behaves" link doing this).
6. **yabai's Requirements/Caveats tables are the elegant version of what Airlock spreads across Install prose.** Airlock's "Requires a COSMIC desktop session (epoch) and Rust 1.93+… On another compositor the daemon exits with a diagnostic" plus the four-distro build-deps code block is the same content yabai puts in a two-column table. Optional, but the table form survives the peer record's bullet-and-code norm better than prose.

**Deliberately NOT copying:**

1. **README-as-banner (alt-tab-macos) or no-README (altdrag).** Both require an owned website/storefront to absorb the README's job. Airlock has a GitHub Pages front door, but the peer record's norm (every peer keeps an informative README) and Rectangle (30k stars, fully informative README) both say the landing-page-only pattern is a scale artifact, not best practice. Also: Airlock's website is a mirror of the same docs, not a distinct storefront, so a banner README would just add indirection.
2. **Badge rows.** Peer norm 4/11 with badges; Airlock ships none; the famous tier shows badges grow with fame and marketing (komorebi's ten include downloads and commercial-license counters) while carrying no install/usage information. Nothing to gain at Airlock's stage.
3. **pop-os/shell's manifesto.** Its "The Proposal"/"The Problem" (~450 words of rhetoric, incl. "Displays are large. Very, **very** large") exists because a first-party team was arguing for GNOME upstreaming. Airlock's Why-as-3-bullets is closer to alttab's single why-sentence, which the peer record already endorsed as the right calibration ("the only peer with a real 'why me' paragraph, and it is one compound sentence").
4. **Komorebi's contributor-policy and integration-API README sections.** ~1,500 of its ~3,000 words are contribution rules and event-subscription API docs — developer material living in the README. Airlock's repo convention already keeps this in `docs/` (vm-development, releasing, hardware-checklist) with a Development section of 3 bullets. Rectangle's one-line link-out ("See [TerminalCommands.md](TerminalCommands.md)") is the pattern to keep.
5. **Gallery-of-three and per-feature screenshots.** Hyprland's gallery works because its product *is* visuals (animations, gradients); Airlock has one overlay card — the single near-top screenshot both tiers agree on is the right size.

**Where this survey disagrees with readme-peer-tone.md (recorded, not resolved):** the peer record's "Troubleshooting: absent from all 11" and "Uninstall: absent from all 11" norms do not hold at the famous tier (Rectangle has both; pop-os/shell and komorebi have undo/recovery paths), so those Airlock sections are tier-legitimate — the famous-tier lesson is to compress them, not to delete them per the peer norm. Likewise the 183-word peer median understates the famous tier (~750 median, estimates): on both tiers the consistent signal is not absolute length but composition — bullets/tables/code carry the content, prose introduces it — and on that measure Airlock's prose-majority body (99 prose vs 12 bullet lines, per the peer record) remains the outlier at both scales.
